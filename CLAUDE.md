This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Purpose

TravelGuide is a menu-driven CLI application that crawls georgiantravelguide.com and stores attraction data in a database, to be used for composing motorcycle routes. Crawl tasks (a name plus start-point URLs) are database entities; each task's submenu has a "Run this task" command (`RunTaskCommand`) that harvests attraction URLs (from the sitemap over HTTP, or from the listing page with Selenium — user's choice at run start) and extracts per-page data over plain HTTP into the `Places` table (see "Task pattern" below).

Code comments are written in Georgian; the user typically communicates in Georgian.

### Menu system

The main menu is assembled by `CliMenuSetFactory.CreateMenuSet("Main Menu", MenuData.MenuCommandNames, ...)`. To add a main-menu item:

1. Create a class implementing `IMenuCommandFactoryStrategy` that builds a `CliMenuCommand` (examples: `TravelGuide/Menu/TravelGuideParametersEdit/TravelGuideParametersEditorListCliMenuCommandFactoryStrategy.cs`, `TravelGuide/MenuCommands/NewTaskCommandFactoryStrategy.cs`), or — for a dynamic group of items — `IMenuCommandListFactoryStrategy` returning one `CliMenuCommand` per item (example: `TravelGuide/MenuCommands/TasksListFactoryStrategy.cs`). The class must be `public` — the DI scanner only sees exported types.
2. Add its name (`nameof(...)`) to `MenuData.MenuCommandNames` (`TravelGuide/Menu/MenuData.cs`). `CliMenuSetFactory` looks the name up among singular strategies first, then list strategies; unmatched names are silently skipped.

Strategies are auto-registered in DI by `AddTransientAllStrategies<IMenuCommandFactoryStrategy>` / `AddTransientAllStrategies<IMenuCommandListFactoryStrategy>` scanning the TravelGuide assembly. Parameters editing UI is `TravelGuideParametersEditor` (field editors per parameter).

The main-menu `Lists` submenu (`ListsSubMenuCommand`) holds DB-backed table editors built on AppCliTools' `Cruder`: `MotorcycleCruder` (a plain `CruderListCliMenuCommand`, record key = `MotorcycleKey`) and the Places editor. `Places` has thousands of rows, so it is not a plain cruder list: `PlacesCommand` asks for an optional name-or-url filter in `RunBody` (Enter = no filter), then `GetSubMenu` shows `New Place` plus one DB-loaded portion (`PlaceCruder.LoadPortion` → `GetPlacesPortion`; portion size from the console height, PageUp/PageDown via the Visits menu's `ChangePortionCommand`) of `PlaceSubMenuCommand` items (name = the caption from `PlaceModelExtensions.GetCaption` (`Menu/PlaceModelExtensions.cs`, also used by `RecommendedPlaceSubMenuCommand`): place `Name`, or `Url` when unnamed, or `Place {PlaceId}` when it has neither; duplicate captions get a ` (N)` suffix; status = `State`, plus ` | Url` when there is one). `PlaceCruder` (`fieldKeyFromItem=true`, record key = that caption — unique within the portion, like `VisitCruder`'s; until 2026-09-15 the key was `Url`) keeps only the last loaded portion as its cruder dictionary — the record menu (Delete / Edit all fields in sequence / read-only `Url` item, present only when the place has a `Url` / field editors) works on those no-tracking copies, so `UpdateRecordWithKey` re-fetches the tracked row by id (`GetPlaceById`) and copies `Name`, `Description`, `State`, `RegionId`, `MunicipalityId`. ### Task pattern (intended crawler workflow)

Tasks are database entities: `TaskModel` plus child `TaskStartPoint`s, managed through `ITravelGuideRepository` (`GetTasksList` / `GetTaskByName` / `CreateTask` / `AddStartPoint` / `SaveChanges`). The main menu's `New Task` item (`TravelGuide/MenuCommands/NewTaskCommand.cs`, wired by `NewTaskCommandFactoryStrategy`) asks for a task name and a start point, checks name uniqueness, and creates a `TaskModel` with one `TaskStartPoint` in a single save. The repository is obtained lazily via `ITravelGuideRepositoryCreatorFactory` inside `RunBody`/`GetSubMenu`/`CreateMenuCommandsList`, so a missing DB configuration surfaces as a caught runtime error instead of a startup crash (if the database hasn't been migrated yet, saves fail gracefully with "Invalid object name 'Tasks'").

Below `New Task`, the main menu lists every task from the DB (`TasksListFactoryStrategy` → one `TaskSubMenuCommand` per task, mirroring the Crawler/CrawlerConsole sibling projects). The per-task submenu offers `Run this task`, `Delete Task`, `Edit Task Name`, `New Start Point`, plus one `StartPointSubMenuCommand` per start point (edit / delete). Convention: destructive/renaming commands return `EMenuAction.LevelUp` (their submenu's identity key is stale), additive ones `EMenuAction.Reload`; menus are rebuilt from the DB on every reload, so lists refresh automatically. `TasksListFactoryStrategy.CreateMenuCommandsList` and `TaskSubMenuCommand.GetSubMenu` must never throw or return null (they run outside `CliMenuCommand.Run`'s exception handling — a throw kills the app), hence their try/catch-and-continue shape.

### Crawler run ("Run this task")

`RunTaskCommand.RunBody` (async) asks up front which way to harvest URLs — sitemap (default) or Selenium listing walk — when the DB already holds `Analysed` places, whether to re-process them, and — only when re-processing was declined and `DownloadError` rows exist — whether to retry those (a "yes" to re-processing retries them implicitly); it also creates the shared `HttpClient` (gzip/brotli decompression, `TravelGuideBot/1.0` UA, `CheckCertificateRevocationList` — CA5399). The whole run is a DB-backed queue (modeled on CrawlerService's `BatchPartRunner`): `EState.New` is the "to download" status, and every persist goes through one shared `HarvestedUrlPersister` instance which trims trailing `/`, dedups per run via `HashSet`, checks every first-seen URL against the DB via `GetPlaceIdsByUrlHashCode` (same-hash rows fetched, exact `Url` compare — `Url` itself carries no index), and **keeps only URLs "like a start point"** — exactly equal to one of the task's start points or under one of them as a path prefix (so the start point value controls crawl scope). When the caller passes the optional source-page URL, the persister also fills `UrlGraphNodes` (which URL was found on which page): pairs are deduped in memory against a once-loaded set, self-links are skipped, and only URLs that exist as `Places` rows can be edge ends (ids come from the run's url→id cache; the source page's id falls back to a hash lookup) — the analyser passes each analysed page, the Selenium walk passes its start point, while seeding and sitemap harvesting pass nothing (no source page, so no edges). Phase 1 seeds the start points themselves as `New` rows, then harvests: sitemap mode (`SitemapUrlHarvester`, no browser) fetches `/sitemap.xml` from the first start point's host and picks the `_ka` sitemap (~4400 URLs, includes non-attraction pages); Selenium mode spins up a fresh `ChromeDriver` per start point and `GeorgianTravelGuideRunner.Run()` walks the listing UI (hard-coded Georgian-caption clicks, infinite-scroll until the URL count stalls), persisting after every scroll batch so an interrupted scroll loses nothing. Phase 2 (`PlaceAnalyser`, browser-free) loops: load a portion via `GetPlacesForAnalysis` (minus PlaceIds already attempted this run), fetch each page with `HttpClient`, parse once with AngleSharp, harvest the page's links via `PageLinkExtractor` (absolutized, http(s)-only, fragment stripped, query-string URLs dropped — search/filter pages would multiply endlessly) into the same persister, then extract data with `PlaceDataExtractor.Extract(document)`; the loop re-queries until no unattempted places remain, so link-discovered pages are processed in the same run, and a cancellation check per page allows clean interruption. JSON-LD is the primary extraction source (`TouristAttraction` name, `BreadcrumbList` region/municipality) with visible-DOM selector fallbacks; coordinates are the exception — both sources are always read and united, because JSON-LD `geo` carries only the *first* location (full precision) while the visible technical-details list carries *all* locations rounded to 6 decimals: each pair is validated against world bounds (lat [-90,90], lon [-180,180] — UTM-style junk like `297267, 4768381` is dropped) and DOM pairs within 1e-5° of an already-taken pair are skipped so the full-precision JSON-LD value wins; the valid pairs become `Locations` rows via `GetOrCreateLocation` and are linked through `PlacesByLocations` by `PlaceLinksSynchronizer.SyncLocations` (diff-based like the other link collections). AngleSharp has no `InnerText`, so `Description` is assembled by a block-aware text walker (source newlines collapse to spaces, block tags become line breaks). Pages without a `TouristAttraction` JSON-LD node (cities/regions/shops — but still link sources) are marked `EState.NotAttraction` and permanently excluded by `GetPlacesForAnalysis`; a page whose request `HttpClient` silently auto-redirected to a different URL (trailing-slash-only differences don't count; detected via `response.RequestMessage.RequestUri`) is marked `EState.Duplicate` without parsing — the final URL is queued as a `New` row (analysed later in the same run) with a `UrlGraphNodes` edge old→canonical, and `Duplicate` rows are permanently excluded from analysis and filtered out of `GetNearestPlaces`; any other failure (HTTP error, exception, missing name) marks the row `EState.DownloadError` — unless cancellation was requested, in which case the analyser exits leaving the row untouched — and such rows are excluded from later runs until the user answers yes to the retry question; the "re-process analysed" answer applies to the first portion only, the retry-errors answer to the whole run. The tracked entity is mutated only after a fully successful extraction (a shared root-scoped DbContext means half-mutated entities would leak into the next `SaveChanges`) — link harvesting for a page therefore runs *before* any mutation — then `State=Analysed` + per-place `SaveChanges`, so an interrupted run resumes naturally.
